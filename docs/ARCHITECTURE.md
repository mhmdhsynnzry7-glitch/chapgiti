# معماری چاپ گیتی

وضعیت ۲۰۲۶/۱۱/۲۴. گفت‌وگوهای پشتیبانی و اعلان‌های هر نقش از SignalR و SQL استفاده می‌کنند. نسخهٔ جاری شرایط نهایی به تأیید مستقل مشتری وابسته است. فرادادهٔ پیوست‌ها با EF و بایت‌ها در فضای خصوصی ذخیره می‌شوند. [راهنمای عملیاتی](WORKFLOW-SUPPORT-OPERATIONS-FA.md)

سابقهٔ معماری ۲۰۲۶/۱۱/۱۷: EF Core 10.0.15 مسیر اصلی persistence است؛ مدل از schema واقعی SQL001–009 در LocalDB موقت استخراج و خط مبنای آن پیش از ثبت اعتبارسنجی می‌شود. کاتالوگ چاپ و مجلهٔ عمومی/مدیریت به SQL متصل‌اند. آن مرحله فقط سورس و آزمون است و دیتابیس کاری، انتشار و بسته‌های قبلی را تغییر نداده است. راهنمای [پذیرش EF](EF-CORE-ADOPTION-FA.md) و گزارش نهایی بر شرح‌های تاریخی مقدم‌اند.

به‌روزرسانی ۲۰۲۶/۱۱/۱۷: پذیرش SQL واقعیِ migrationهای ۰۰۸/۰۰۹ و گردش اصلاحیه/مشاهده روی دو نمونهٔ اختصاصی SQL Server 2019 LocalDB 15.0.4382.1 موفق شد. دیتابیس کاری خوانده یا فعال نشد و fixtureها حذف شدند. نتایج، محدودهٔ اعتبار و فعال‌سازی بعدی.

در مرحلهٔ ۲۰۲۶/۱۱/۱۶ گردش اصلاحیه، آمادگی چاپ و مشاهدهٔ مستقل سفارش پیاده‌سازی شدند. قرارداد جاری پشتیبانی و پیوست‌ها در راهنمای پشتیبانی مستند شده است. [قرارداد سفارش](ORDER-CORRECTIONS-AND-ATTENTION-FA.md)

به‌روزرسانی ۲۰۲۶/۱۱/۱۴: SignalR فقط برای اعلان مشتری، اعلان مدیر و گفت‌وگوی پشتیبانی افزوده شده است. SQL و REST منبع معتبر باقی‌اند؛ hintها پس از commit و پایان تراکنش ارسال می‌شوند، نشست و مالکیت پیش از تحویل دوباره بررسی می‌شود و polling fallback حفظ شده است. جدول یا migration جدید ندارد. [قرارداد، امنیت و نیازمندی‌های پراکسی](SIGNALR-REALTIME-FA.md).

به‌روزرسانی بیزینس و UI در ۲۰۲۶/۱۰/۳۰: جزئیات نمونه‌کار با ID موجود در `/portfolio/[slug]`، پیگیری اصلی در حساب مشتری، metadata فایل‌های مالک، قالب مشترک تومان و بخش مستقل تعرفه‌های تکمیلی اضافه شدند. فهرست مدیریت روی focus تازه‌سازی می‌شود. سابقهٔ ورود از Auth_Sessions موجود خوانده می‌شود و schema جدید لازم نیست. شرح قراردادها، ماتریس خدمات، بررسی سفارش گزارش‌شده و نتایج واقعی تست‌ها در گزارش تغییرات است.

این مخزن دو پروژهٔ مستقل دارد: frontend برای React / Next.js و backend برای ASP.NET Core. هر پروژه به‌تنهایی نصب، build و اجرا می‌شود. اسکریپت‌های ریشه صرفاً اجرای هم‌زمان و بسته‌بندی IIS را ساده می‌کنند.

## مسیر درخواست

مرورگر ← Next.js (SSR و پروکسی app/api) ← ChapGiti.Api ← ChapGiti.Application ← قرارداد Repository ← ChapGiti.Infrastructure ← SQL Server.

Domain توسط Application استفاده می‌شود و هیچ ارجاعی به لایه‌های دیگر ندارد. API تنها محل اتصال پیاده‌سازی‌های Infrastructure به قراردادهای Application است. رابط سایت، قرارداد JSON و خطاهای فارسی قبلی حفظ شده‌اند.

## مسئولیت لایه‌ها

Domain شامل فرمول‌های چاپ، اعتبارسنجی مشخصات، گزینه‌های چاپ و قوانین گردش سفارش و تیکت است.

Application شامل use caseهای نام‌گذاری‌شده مانند ایجاد سفارش، محاسبهٔ هزینه، تکمیل حساب و پاسخ تیکت است. این لایه به interfaceهای ذخیره‌سازی، فایل، هش رمز، نشست و پیامک وابسته است. خروجی UseCaseResult مستقل از IResult در ASP.NET است. Read modelهای دیکشنری برای حفظ قرارداد JSON فعلی پنل به‌کار می‌روند؛ آن‌ها API اجرای SQL ندارند.

Infrastructure شامل ChapGitiDbContext، Fluent mappings و Repositoryهای EF Core است. CRUD عادی حساب/نشست/سفارش/قیمت/اصلاحیه/تنظیمات/اعلان از EF استفاده می‌کند. SQL پارامتری فقط برای قفل‌ها، idempotency اتمیک، OTP سازگار با CHECK، آرشیو پیچیده و ابزار تاریخی باقی مانده است؛ فهرست دقیق در گزارش پذیرش EF آمده است. Application هیچ DbContext، SQL یا پیاده‌سازی concrete دریافت نمی‌کند.

API مسیرها و متد HTTP را به متدهای Application وصل می‌کند. کوکی‌های HttpOnly، بررسی origin، خواندن محدود بدنه و تبدیل خطا و پاسخ در این لایه قرار دارند.

## مرزهای مهم

- IUnitOfWork و Repositoryها یک SqlStore در scope مشترک دارند؛ ثبت سفارش و رویداد و کنترل نسخه اتمیک می‌مانند.
- مالکیت سفارش و تیکت با شناسهٔ حساب بررسی می‌شود. خواندن بدنهٔ فایل پس از بررسی مالکیت انجام می‌شود.
- IPrivateFileStore کلید فایل می‌گیرد؛ مسیر دیسک داخل Infrastructure پنهان است.
- IRequestSession به API اجازه می‌دهد توکن نشست را با کوکی منتقل کند؛ منطق نشست و دسترسی در Application است.
- IPasswordHasher پیاده‌سازی PBKDF2 و سازگاری با scrypt قبلی را جدا می‌کند.
- ISmsNotifier فقط وضعیت پیکربندی و عملیات ارسال را در اختیار use case می‌گذارد. اطلاعات ورود ملی‌پیامک در Infrastructure می‌ماند.
- SQL و فایل‌های پیش‌فرض همراه بک‌اند نسخه‌بندی می‌شوند. build بک‌اند اسکریپت npm اجرا نمی‌کند.
- frontend/lib شامل پیش‌نمایش قیمت است؛ مبلغ سفارش همیشه دوباره در Domain بک‌اند محاسبه می‌شود. آزمون تطبیقی قیمت، اختلاف دو پیاده‌سازی را بررسی می‌کند.
- ابزار generate-dotnet-defaults فقط برای همگام‌سازی عمدی تعاریف توسط توسعه‌دهنده است و بخشی از build نیست. پس از تغییر گزینه‌های چاپ، خروجی JSON را بازبینی و آزمون تطبیقی را اجرا کنید.

## توسعه و کنترل وابستگی‌ها

استثنای مجاز آزمون SQL: `tests/sql005` با flag صریح و مجوز همان کار، در یک نمونهٔ LocalDB مستقل زنجیرهٔ migration و APIهای واقعی را با دادهٔ ساختگی بررسی می‌کند. این ابزار بخشی از startup یا تست‌های پیش‌فرض نیست و به تنظیمات SQL عملیاتی دسترسی نمی‌گیرد. نتیجهٔ پذیرش و اصلاح نوع ستون یادداشت در گزارش SQL 005 آمده است. قواعد زیر دربارهٔ اسکریپت‌ها و مسیرهای معمول برنامه همچنان برقرارند.

برای افزودن قابلیت، قانون مربوط را در Domain، عملیات را در Application و نیاز خارجی را به‌صورت interface تعریف کنید. پیاده‌سازی در Infrastructure و مسیر HTTP در API اضافه شود.

آزمون `npm run test:architecture` جهت وابستگی اسمبلی‌ها و مرزهای Domain و Application را بررسی می‌کند. بررسی عملیاتی دیتابیس خواندنی است. آزمون نوشتنی `tests/sql005` با آرگومان `--authorize-disposable-ef-activation` نصب تازه و ارتقا را با دادهٔ مصنوعی در SQL Server LocalDB اختصاصی اجرا می‌کند.

tools/legacy-sqlite فقط ابزار سازگاری مهاجرت است و در اجرای سایت وارد نمی‌شود. data و .env.local و کلیدهای پیامک داخل بستهٔ سورس و انتشار قرار نمی‌گیرند.


## یک دیتابیس موجود

Migrations مستقیماً به catalog پیکربندی‌شده متصل می‌شود؛ اتصال به master برای provision کردن و ساخت خودکار دیتابیس حذف شده است. پایگاه‌دادهٔ اصلی ChapGiti حفظ می‌شود. ساخت fixtureهای مستقل و تغییر نام دیتابیس با شناسهٔ تصادفی از مسیر آزمون‌ها حذف شده است.

## مدیریت محتوای خدمات و ساختار محصول V2

خدمات عمومی از `Settings.services` خوانده می‌شوند؛ شش خدمت قبلی در defaults بک‌اند با شناسهٔ پایدار حفظ شده‌اند. نبودن کلید، فقط باعث خواندن همین پیش‌فرض می‌شود؛ اولین ذخیرهٔ صریح مدیر، فهرست کامل را در SQL ثبت می‌کند. startup و خواندن صفحات داده‌ای نمی‌نویسند. خدمات محتوایی از شناسه‌ها و قواعد قیمت‌گذاری سفارش مستقل‌اند.

`AdminServicesController` و `PublicContentController` ورودی HTTP هستند. `ServiceContentService` اعتبارسنجی، انتشار، نسخه، ترتیب و یکتایی slug/alias را انجام می‌دهد. نوشتن روی کلید services با قفل `UPDLOCK/HOLDLOCK` در تراکنش serializable و ثبت audit انجام می‌شود؛ نسخهٔ قدیمی با 409 رد می‌شود. جدول Settings موجود با Repository EF خوانده و نوشته می‌شود؛ قفل UPDLOCK/HOLDLOCK روی اتصال/تراکنش مشترک EF حفظ شده است.

Next.js خدمات منتشرشده را از bootstrap بک‌اند به‌صورت SSR نمایش می‌دهد؛ عنوان، توضیح سئو و canonical از محتوای ذخیره‌شده می‌آیند. تغییر slug، alias قبلی را نگه می‌دارد؛ مسیر قبلی عمومی به canonical با 308 هدایت می‌شود. خدمت غیرفعال در API عمومی و صفحات در دسترس نیست. تصویر اختیاری از زیرساخت موجود banner-assets می‌آید و در نبود تصویر، تصویرسازی قبلی استفاده می‌شود.

کارت و جزئیات خدمات به مشاوره در `/contact` پیوند دارند. مشتری از `/tickets` پشتیبانی عمومی و از جزئیات سفارش گفت‌وگوی همان سفارش را باز می‌کند. پاسخ، پیوست و وضعیت تیکت مستقل از تأیید رسمی فایل و قیمت هستند.

دکمهٔ بنر یک جفت اختیاری label/link است؛ نبودن هر دو، هیچ دکمه یا پیوند روی کل بنر ایجاد نمی‌کند. اطلاعات سایت سه کلید اختیاری `instagram`، `telegram` و `bale` دارد؛ فقط URLهای HTTPS با میزبان و قالب معتبر همان شبکه پذیرفته می‌شوند. مشتری قدیمی API که این فیلدها را نمی‌فرستد مقادیر ذخیره‌شده را پاک نمی‌کند.

مجله از Articles موجود با وضعیت پیش‌نویس/منتشرشده/بایگانی، نسخه، تصویر و alias نشانی استفاده می‌کند. /blog و /blog/[slug] و /admin/articles فعال‌اند؛ API و SSR و sitemap فقط محتوای منتشرشده را نشان می‌دهند. نمونه‌کار و CTA محاسبه/سفارش پایین مقاله همچنان غیرفعال‌اند. آرایه‌های قدیمی bootstrap برای سازگاری خالی می‌مانند و مقاله‌ها از API جداگانهٔ صفحه‌بندی‌شده خوانده می‌شوند.

`Pagination` و `paginationState` صفحه‌بندی مشترک RTL را برای سفارش‌ها، مشتریان، تیکت‌ها و فعالیت‌ها فراهم می‌کنند؛ اندازهٔ صفحه و مالکیت همچنان در API کنترل می‌شوند. فیلترها به صفحهٔ اول برمی‌گردند؛ تازه‌سازی صفحهٔ معتبر را حفظ می‌کند و کاهش تعداد نتایج به صفحهٔ معتبر هدایت می‌شود.


## حساب، مجوز و نشست مستقل مشتری و مدیر

CustomerOtpService ثبت‌نام، تأیید شماره و بازیابی مشتری را با OTP انجام می‌دهد؛ ورود مشتری موبایل و رمز می‌خواهد. ورود مدیر در `/admin/login` با نام ثابت `admin` و رمز فعلی است. نگاشت موجود Admin_Usernames حساب را مشخص می‌کند؛ تغییر ایمیل پروفایل روی نام ورود و شناسه حساب اثر ندارد. SessionService موتور مشترک صدور و چرخش توکن دارد، ولی دو حوزهٔ مستقل را با کوکی‌ها، namespace هش و نوع principal جدا می‌کند. مشتری حتی با نقش تاریخی admin، نشست مدیریت ندارد. هر خانواده در Auth_Sessions فقط یکی از customer_id یا legacy_admin_email را دارد؛ هیچ نقش مشتری به‌عنوان مجوز نشست مدیریت استفاده نمی‌شود.

ثبت‌نام: موبایل → OTP کنسول → مجوز ثبت‌نام → مشخصات و رمز → ساخت حساب. `otp/request` فقط شماره و هدف می‌گیرد و `otp/verify` به‌جای حساب، مجوز پنج‌دقیقه‌ای برمی‌گرداند. `registration/complete` مشخصات و رمز را با مجوز معتبر دریافت می‌کند؛ شماره فقط از مجوز سرور خوانده می‌شود. ایجاد پروفایل، تأیید شماره، هش رمز و مصرف مجوز در یک تراکنش با قفل امنیت، شماره و ردیف انجام می‌شوند. مجوز فقط در حافظهٔ فرم است؛ ورود همچنان مرحله‌ای مستقل با موبایل و رمز است.

بدون تغییر schema، مجوزها در ردیف‌های جداگانهٔ Customer_Otp_Challenges ذخیره می‌شوند؛ id فقط هش کامل توکن با تفکیک هدف و حالت واقعی/توسعه است. قید CK_OtpDelivery فقط pending، sent و failed را می‌پذیرد؛ نوشتن grant باعث SQL 547 و پاسخ عمومی 500 می‌شد. وضعیت منطقی grant اکنون در Infrastructure با ترکیب purpose=register، delivery_status=pending، attempts=5 و code_hash=NULL کدگذاری می‌شود. چالش پیامکِ در انتظار همیشه صفر تلاش دارد؛ چالشِ با تلاش تمام‌شده sent است. این ترکیب به وضعیت منطقی grant نگاشت می‌شود و حتی پس از مصرف/ابطال از شمارش پیامک و cooldown کنار می‌رود. مجوز با درخواست کد تازه باطل می‌شود و هیچ کد OTP در آن نیست. دادهٔ جدول Pending_Customer_Registrations تاریخی حفظ می‌شود؛ جریان جدید از آن استفاده نمی‌کند. migration یا تغییری در رکوردهای عملیاتی انجام نشده است.

ورود مشتری پس از یکسان‌سازی ارقام موبایل، برای حساب ناموجود کد `CUSTOMER_ACCOUNT_NOT_FOUND` و برای رمز اشتباه حساب موجود کد `CUSTOMER_PASSWORD_INCORRECT` را با HTTP 401 برمی‌گرداند. رابط کاربری پیام فارسی و لینک ثبت‌نام را از روی کد انتخاب می‌کند؛ شماره در وضعیت محلی فرم حفظ می‌شود و وارد URL نمی‌شود. محدودیت تلاش‌ها و بررسی رمز ساختگی برای حساب ناموجود حفظ شده‌اند؛ خطای مدیر و پاسخ عمومی بازیابی رمز تغییری ندارند. تست‌های HTTP و مرورگر از مخزن حافظه‌ای و پیامک ساختگی استفاده می‌کنند؛ `npm.cmd run test:customer-login-errors` نگاشت کد به پیام را مستقل بررسی می‌کند.

AdministratorService تغییر ایمیل خود مدیر و تغییر رمز با تأیید رمز فعلی را انجام می‌دهد. فهرست حساب‌ها فقط خواندنی است و ایجاد مدیر اضافی در مدل نام ثابت رد می‌شود؛ هیچ حساب تاریخی حذف یا بازنویسی نمی‌شود. endpoint پروفایل شناسهٔ هدف نمی‌پذیرد. تغییر رمز همهٔ نشست‌های همان مدیر را باطل می‌کند و به مشتری دست نمی‌زند. Domain/Authentication/PasswordPolicy مرجع رمزهای جدید و تغییریافته است: ۶ تا ۱۲۸ نویسه، A–Z و نشانهٔ ASCII؛ ورود رمزهای تاریخی به پیچیدگی جدید وابسته نیست.

migration افزایشی 004 شامل login_email و ستون محاسباتی unique effective_email است، بدون تغییر کلید تاریخی Admin_Users.email. این migration در 2026-10-30 با مجوز صریح مالک روی Development محلی اعمال شد. مخزن‌ها در محیط‌های فاقد 004 همچنان برای ورود، نشست، فهرست و رمز از ستون قدیمی استفاده می‌کنند؛ فقط تغییر ایمیل در آن محیط‌ها فعال نیست. شروع برنامه به 004 وابسته نشده است. جزئیات تاریخی در ADMIN-AUTH-PASSWORD-REPORT-FA.md و اصلاح نام ورود در ADMIN-USERNAME-CORRECTION-FA.md آمده است.

در اتصال کنسول ملی‌پیامک، IOtpSender همان code تولیدشده و ارسال‌شده توسط ارائه‌دهنده را تحویل Application می‌دهد. CustomerOtpService کد دیگری تولید نمی‌کند؛ فقط HMAC وابسته به شماره، هدف و شناسهٔ چالش را از طریق IOtpRepository ذخیره می‌کند. RandomNumberGenerator در این جریان شناسهٔ چالش و مجوز بازیابی می‌سازد، نه کد پیامک. status متن تشخیصی است؛ پذیرش آداپتور به HTTP موفق، ساختار معتبر پاسخ و کد عددیِ هم‌اندازهٔ تنظیم وابسته است. خطای ارائه‌دهنده بدون کد قابل استفاده، حتی با HTTP 200، چالش قابل تأیید ایجاد نمی‌کند.

IRequestSession فقط انتقال HttpOnly cookie را به API می‌سپارد. IAccessSessionRepository خانوادهٔ نشست/هش مجوزها، IUserManagementRepository فهرست و نقش و IOtpRepository چالش و اطلاعات موقت ثبت‌نام را ذخیره می‌کنند. پیاده‌سازی SQL و ملی‌پیامک فقط در Infrastructure است. migration 003 افزایشی در تاریخ 2026-10-27 با مجوز صریح و پس از بکاپ تأییدشده روی ChapGiti محلی اعمال شد؛ رکوردهای قبلی بازنویسی نشدند. شروع معمول همچنان فقط --check اجرا می‌کند و محیط‌های دیگر نیازمند مجوز مستقل‌اند.

## Controller و قراردادها

بازیابی رمز پیش از ایجاد چالش یا ارسال پیامک، حساب واقعی Customer_Accounts متصل به Customer_Registrations، مشخصات کامل و phone_verified را بررسی می‌کند. ثبت‌نام موقت و مجوز OTP به‌تنهایی حساب نیستند. حساب ناموجود با CUSTOMER_ACCOUNT_NOT_FOUND و حساب ناقص/شمارهٔ تأییدنشده با خطای اختصاصی رد می‌شود. این بررسی هنگام تأیید هم زیر قفل امنیت و شماره تکرار می‌شود؛ ابطال چالش نامعتبر و شمارش تلاش اشتباه پیش از پرتاب خطای ساختاریافته commit می‌شوند. schema و اطلاعات عملیاتی تغییری نمی‌کنند.

ChapGiti.Api/Controllers مسیرهای قبلی را حفظ کرده و ApiDispatcher حذف شده است. ApiRegistration ترکیب MVC و نگاشت سلامت را متمرکز می‌کند. ApiSecurityFilter پیش از model binding مبدأ را بررسی می‌کند و RequireAdministrator نشست مستقل مدیر را در بک‌اند می‌سنجد. قراردادهای ورودی حساب، پروفایل، ایجاد کاربر و نقش typed هستند و فیلد ناشناخته را رد می‌کنند؛ مدل‌های پاسخ حساب و کاربر در Application/Authentication قرار دارند. UseCaseResult همچنان مستقل از IResult است.

فرانت هیچ نقش یا قیمت معتبری صادر نمی‌کند. تمدید در مرورگر از مسیر هم‌مبدأ انجام می‌شود؛ SSR برای کوکی منقضی‌شدهٔ مشتری به /session/renew و برای مدیر به /admin/session-renew هدایت می‌کند. HTTP عمومی اجازهٔ صدور/تمدید نشست ندارد؛ استثنا فقط loopback در Development است.

جزئیات سیاست، API، محدودیت HTTP، مهاجرت حساب قدیمی و روش آزمون در CUSTOMER-AUTH-OTP-FA.md و MODERNIZATION-REPORT-FA.md آمده است. test:auth و test:ui از دادهٔ حافظه‌ای استفاده می‌کنند؛ آزمون SQL تغییردهنده بدون محیط ایزولهٔ مجاز اجرا نمی‌شود.

## تنظیم محلی تأیید OTP

OtpVerificationPolicy در Application فقط حالت صدور/تأیید چالش را تعریف می‌کند؛ OtpVerificationConfiguration در Infrastructure محیط و تنظیم را اعتبارسنجی می‌کند. API این سیاست را هنگام startup resolve می‌کند تا false در محیط غیرمحلی یا غیر Development فوراً رد شود. پیش‌فرض همهٔ محیط‌ها، از جمله Development، OTP_VERIFICATION_ENABLED=true است. تنظیم محلی OTP_ENABLED=true و SMS_ENABLED=true نیز فعال است؛ credential خصوصیِ کنسول و پیامک سفارش جداگانه لازم‌اند. نبود credential باعث bypass نمی‌شود.

در حالت اختیاریِ false برای تست محلی، چالش با marker غیرمحرمانهٔ ۶۴نویسه‌ای در ستون موجود code_hash به همان چرخهٔ درخواست/انقضا/مصرف متصل می‌شود. کد دقیقاً چهاررقمی پذیرفته می‌شود، اما حالت عادی marker را قبول نمی‌کند. هش مجوز بازیابیِ محلی نیز namespace مستقل دارد. نیازی به تغییر schema یا بازنویسی داده نیست. هر دو آداپتور پیامک در حالت false غیرفعال‌اند. UI همان قرارداد JSON و مراحل پیشین را استفاده می‌کند. جزئیات و محدودیت‌ها در CUSTOMER-AUTH-OTP-FA.md آمده است.

## درخواست، پیشنهاد و تولید

مشخصات مرجع در [PRODUCT-ARCHITECTURE-FA.md](PRODUCT-ARCHITECTURE-FA.md) و جزئیات اجرا در CHAP-REQUEST-TO-PRINT-IMPLEMENTATION.md هستند. محاسبهٔ تقریبی بدون ورود با POST /api/quote محدودشده و معتبر انجام می‌شود؛ ساخت درخواست و تصمیم‌ها نشست مشتری کامل می‌خواهند. فقط مشخصات فنی allowlist شده در sessionStorage همان برگه برای بازگشت ورود می‌مانند؛ نام، تماس، رمز، OTP، مجوز، یادداشت و فایل در draft نیستند.

`OrderQuoteService` عملیات را با `IOrderQuoteRepository` و قفل سفارش موجود هماهنگ می‌کند. `QuoteWorkflow` و `OrderWorkflow` قواعد Domain را نگه می‌دارند و کنترلرها نازک‌اند. شرایط تجاری در `Order_Quotes` نسخهٔ تازه می‌گیرند؛ نسخهٔ ارسال‌شده بازنویسی نمی‌شود. پذیرش مالک، وضعیت quote، مبلغ نهایی و صف چاپ را اتمیک می‌کند. `Order_Commands` رسید actor/payload-bound برای retry ایمن دارد؛ نسخهٔ سفارش و پیشنهاد نیز بررسی می‌شوند.

درخواست اطلاعات/PDF با پرچم اقدام مشتری در review می‌ماند؛ گفتگوی پشتیبانی وضعیت پیشنهاد را خودکار تغییر نمی‌دهد. تایم‌لاین از Events و مرکز اعلان از projection پایدار خودش می‌خواند؛ شبکهٔ realtime یا شرط اجباری پیامک اضافه نشده است. مشتری فقط projection عمومی quote را می‌گیرد؛ یادداشت اجرایی، نویسندهٔ مدیریتی و رسیدهای فرمان خصوصی‌اند.

مرکز اعلان نسخهٔ ۳ اکنون projection پایدار مجزایی دارد: Domain/Notifications/BusinessNotification رویداد مستقل از کانال را تعریف می‌کند؛ NotificationPublisher متن امن و گیرندهٔ معتبر را به INotificationRepository می‌سپارد، داخل همان تراکنش سفارش/پیشنهاد/پیام. فرانت هر حوزه provider مستقل با کلید هویت دارد: زنگ، dropdown پنج‌تایی و صفحهٔ بیست‌تایی. شمارنده با polling سریالی ۲۰ثانیه‌ای، فوکوس و mutation موفق تازه می‌شود؛ در تب مخفی تایمر متوقف است. read/read-all با BroadcastChannel همان حوزه بین تب‌ها هماهنگ می‌شوند؛ هیچ دادهٔ خصوصی در پیام کانال نیست. بازکردن فهرست read نیست؛ انتقال لینک پس از پاسخ موفق read انجام می‌شود. خطای اعلان مسیر اصلی را مسدود نمی‌کند. هیچ API Push، permission، service worker، device token یا SMS تازه‌ای اضافه نشده است. موبایل آینده می‌تواند از eventType/entityKind/entityId استفاده کند؛ هر کانال خارجی و outbox لازمِ آن، فاز مستقل می‌خواهد.
