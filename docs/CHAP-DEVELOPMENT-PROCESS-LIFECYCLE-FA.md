# اجرای توسعه و مدیریت پورت‌های چاپ گیتی

در PowerShell معمولی یا ترمینال PowerShell در VS Code از ریشهٔ پروژه اجرا کنید.

```powershell
Set-Location 'C:\src\chapgiti'
npm.cmd run dev
```

سایت روی `http://127.0.0.1:3000/` و سلامت API روی `http://127.0.0.1:5100/health` است. برای توقف در همان ترمینال Ctrl+C را بزنید. از ترمینال دوم در همین پوشه می‌توانید وضعیت را ببینید یا نشست را ببندید.

```powershell
npm.cmd run dev:status
npm.cmd run dev:stop
```

### علت تداخل

در ابتدای بررسی، PID ‏30096 روی ۵۱۰۰، DLL همین پروژه را از پوشهٔ Debug با آرگومان `--main-development` اجرا می‌کرد. PID ‏30624 روی ۳۰۰۰ فرزند Next.js همین مسیر بود. زنجیرهٔ هر دو به PID ‏20204 و راه‌انداز قبلی می‌رسید. بنابراین علت مشاهده‌شده برای برخورد پورت، وجود یک نشست زنده بود. برای خطای قدیمی 10048 به‌تنهایی نمی‌توان تعیین کرد که والد در آن لحظه زنده بوده است یا خیر.

راه‌انداز قبلی دو برنامه را بدون بررسی پورت و ثبت هویت شروع می‌کرد. شنود Ctrl+C بعد از رسیدن API به مرحلهٔ آماده و ساخت فرایند فرانت نصب می‌شد. پایان ناگهانی والد یا خروج زودهنگام در این فاصله می‌توانست فرایندی را باقی بگذارد. شنوندهٔ ۳۰۰۰ معمولاً فرزند CLI فرانت است. بررسی صرف PID مربوط به CLI برای احراز آزاد شدن پورت کافی نیست.

### رفتار راه‌انداز ویندوز

- پیش از build یا دسترسی برنامه به دیتابیس، مالک هر دو پورت و امکان bind روی IPv4 loopback بررسی می‌شود. در برخورد با نشست فعال، شروع دوم با کد غیرصفر پایان می‌یابد. آدرس پورت خودکار عوض نمی‌شود.
- فایل‌های `.qa/dev-processes/<session-id>.json` فقط در همین checkout ذخیره می‌شوند. هر فایل مسیر مخزن، شناسهٔ تصادفی نشست و هویت فرایندها شامل PID و زمان ایجاد را نگه می‌دارد. برای فرانت، PID ریشهٔ CLI ثبت می‌شود و `dev:status` PID شنوندهٔ واقعی را از سیستم‌عامل می‌گیرد. پوشهٔ `.qa` در Git نادیده گرفته می‌شود.
- تشخیص مالکیت از مسیر دقیق DLL توسعه، آرگومان‌ها، مسیر اسکریپت‌های Next، ترتیب ایجاد والد و فرزند و هویت میزبان نشست استفاده می‌کند. برای PID بازیافتی یا مالک ناشناس، دستور توقف مجوز پایان دادن به فرایند را از فایل PID نمی‌گیرد. `dev:status` فقط می‌خواند. در خروجی فرایند ناشناس، نام و مسیر اجرایی در صورت دسترسی نمایش داده می‌شود و آرگومان‌های آزاد که ممکن است حاوی رمز باشند پنهان می‌مانند.
- هر نشست یک Windows Job Object دارد. نام آن از مسیر همین مخزن مشتق می‌شود تا دو اجرای هم‌زمان نتوانند هر دو مالک نشست شوند. worker فقط پس از عضویت در Job اجازهٔ ایجاد فرزند دارد. build، بررسی دیتابیس، بک‌اند، CLI فرانت و فرزندان آن در همان Job اجرا می‌شوند. برای دریافت توقف، میزبان هم به پایان لولهٔ والد و هم به رویداد اختصاصی همان نشست گوش می‌دهد.
- Ctrl+C و `dev:stop` ابتدا توقف عادی را در کنسول خصوصی نشست درخواست می‌کنند. میزبان تا ۶٫۵ ثانیه برای پایان فرایندها صبر می‌کند. اگر فرزندی باقی مانده باشد یا خود میزبان ناخواسته از بین برود، ویندوز اعضای همان Job را می‌بندد. خطای شروع یک مؤلفه روی stderr اصلی باقی می‌ماند و خروج غیرمنتظرهٔ آن با `BACKEND_EXIT` یا `FRONTEND_EXIT` گزارش می‌شود. خطاهای پیکربندی SQL و migration از همان بررسی قبلی بک‌اند گزارش می‌شوند. [مستند Job Objects مایکروسافت](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) · [دامنهٔ دریافت Ctrl+C در ویندوز](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent)
- در اجرای بعدی، یک شنوندهٔ قدیمیِ بدون والد معتبر فقط با اثبات مالکیت همین نسخهٔ Development قابل پاک‌سازی است. برای نشست قدیمی زنده، دستور صریح `dev:stop` لازم است. در مسیر بازیابی، زمان ایجاد بلافاصله پیش از توقف روی handle همان فرایند دوباره بررسی می‌شود. اگر توقف عادی آن فرایند در دسترس نباشد، فقط همان فرایند تأییدشده پایان داده می‌شود. دستور توقف در صورت باقی‌ماندن نشست یا اشغال بودن پورت موفقیت اعلام نمی‌کند.

### دامنهٔ تغییر فایل‌ها

| فایل | تغییر |
|---|---|
| `package.json`، `scripts/dev-dotnet.mjs` | فرمان‌های شروع، وضعیت، توقف و تست ابزار توسعه |
| `scripts/dotnet-runtime.mjs` | استفادهٔ مشترک از حذف متغیرهای محرمانه برای فرانت و پشتیبانی از کنسول خصوصی در build و بررسی توسعه |
| `scripts/development/processes.mjs` | بازرسی پورت و فرایند، تشخیص مالکیت، ثبت نشست و بررسی آزاد شدن پورت‌ها |
| `scripts/development/worker.mjs` | اجرای build، بررسی فقط‌خواندنی دیتابیس، کنترل هویت شنوندهٔ health و راه‌اندازی فرانت |
| `scripts/development/windows-session.ps1`، `scripts/development/WindowsDevJob.cs` | بررسی ویندوز، مدیریت Job، توقف عادی و جمع‌آوری درخت فرایند |
| `tests/development/process-lifecycle.test.mjs`، `tests/development/job-fixture.mjs` | سناریوهای مالکیت و خطا، همراه با فرایندها و پورت‌های آزمایشی مستقل |
| `README.md` و همین راهنما | دستورهای روزمره و شواهد آزمون |

### حدود آزمون

۲۰ آزمون هدفمند ابزار توسعه موفق شدند. آزمون‌های هویت و بازیافت PID از دادهٔ ساختگی استفاده کردند. آزمون Job Object روی ویندوز با فرایندهای واقعی آزمایشی انجام شد و قطع والد، مرگ خود میزبان، شکست هر یک از دو سرویس، خروج درخت فرزندان و باقی‌ماندن شنوندهٔ مستقل را بررسی کرد. هفت رد هدف دیتابیس درون یکی از همین آزمون‌ها اجرا شد. حفظ متن خطای migration با خروجی شبیه‌سازی‌شدهٔ مرحلهٔ check آزموده شد. در دیتابیس اصلی migration عمداً معلق ایجاد نشد. خروجی آزمون ابزار توسعه
