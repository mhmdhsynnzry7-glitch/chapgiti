# پشتیبانی، توافق سفارش و تحویل دستی

## تیکت و توافق نهایی

سفارش مشتری، در صورت وجود، به گفت‌وگوی باز همان سفارش لینک می‌دهد. مدیر می‌تواند وضعیت «منتظر پاسخ مشتری» را صریحاً انتخاب کند. پاسخ عادی مدیر تیکت باز را باز نگه می‌دارد. پاسخ مشتری آن را به صف پشتیبانی برمی‌گرداند. فقط پیام طرف مقابل در شمارندهٔ خوانده‌نشده حساب می‌شود.

فرم پاسخ مشتری و مدیر PDF، JPEG، PNG و WebP را می‌پذیرد. سرور نام، ساختار باینری و حدود تعداد و حجم را کنترل می‌کند. مقدار پیش‌فرض سه پیوست و چهار MiB برای هر فایل است. می‌توان در پیکربندی سرویس `Support__MaxAttachments` و `Support__MaxAttachmentBytes` را کاهش داد. پاسخ GET تیکت حدود مؤثر را به فرم برمی‌گرداند. سقف کل درخواست HTTP شانزده MiB است.

بایت‌ها در `DATA_DIR/ticket-files/<GUID>` و فراداده در `dbo.Ticket_Attachments` نگهداری می‌شوند. دانلود از مسیر احرازشدهٔ `GET /api/tickets/{ticketId}/attachments/{fileId}` یا مسیر هم‌ارز مدیر صورت می‌گیرد. نام ذخیره از شناسه ساخته می‌شود. فرادادهٔ پیام‌های یک تیکت در یک پرس‌وجو خوانده می‌شود. درخواست چندبخشی `POST .../messages/attachments` کلید ارسال، متن و فایل‌ها را می‌گیرد. برای ایجاد همراه فایل، POST /api/tickets/attachments موضوع، متن، orderId اختیاری، کلید ارسال و فایل‌های پیام اول را در همان تراکنش ثبت می‌کند. ثبت و پاسخ متنی از مسیرهای JSON پیشین انجام می‌شوند. درج فراداده، پیام و اعلان یک تراکنش است. تکرار همان کلید و محتوا به همان پیام می‌رسد. فایل تیکت در فرایند تأیید PDF تولید شرکت نمی‌کند. بکاپ دادهٔ خصوصی باید پوشهٔ پیوست را همراه دیتابیس پوشش دهد.

شرایط نهایی در snapshot موجود سفارش با شناسه، شمارهٔ نسخه، فایل، پیشنهاد و مشخصات مرتبط نگهداری می‌شود. اصلاح نسخهٔ جاری نیازمند `revisionOf` و `expectedVersion` است. تاریخ تأیید قبلی در تاریخچه باقی می‌ماند. تولید به پذیرش نسخهٔ جدید وابسته است. دسترسی مدیر و مشتری، قیمت پذیرفته‌شده و PDF معتبر در سرور کنترل می‌شود.

## ساخت Release در آینده

پس از Merge و تأیید Release توسط مالک، از checkout تمیز همان commit روی ویندوز با نسخه‌های مستند Node و .NET اجرا شود. این دستورات برای تحویل آینده‌اند.

```powershell
npm.cmd --prefix frontend ci
npm.cmd run publish:backend
if ($LASTEXITCODE -ne 0) { throw 'Backend publish failed' }
npm.cmd run publish:frontend
if ($LASTEXITCODE -ne 0) { throw 'Frontend publish failed' }
npm.cmd run package:iis -- --release-only
if ($LASTEXITCODE -ne 0) { throw 'Release verification failed' }
```

قبل از تعویض نسخهٔ نصب‌شده، مالک باید SHA-256 بسته، نسخه و سازگاری SQL، مسیرهای خصوصی و بکاپ قابل بازیابی مقصد را طبق راهنمای Windows Server بررسی کند. با توقف نویسنده‌ها، از داخل ریشهٔ Release روی مقصد تأییدشده، `$env:NODE_ENV = 'production'` و سپس `npm.cmd run db:setup` اجرا شود. باید `20261124131104_TicketMessageAttachments` در EF history، کلید خارجی به پیام تیکت و ایندکس یکتای پیام و ترتیب فایل وجود داشته باشند. پس از آن می‌توان نسخهٔ برنامه را فعال کرد و health، دو نقش و دانلود خصوصی را بررسی کرد. روی میزبان چندسایته، Binding و تنظیمات IIS را طبق راهنمای همان نصب انتخاب کنید. [راهنمای نصب ویندوز](WINDOWS-SERVER-INSTALL-FA.md)

## سئو و Search Console

روی سرور HTTPS صحیح و canonical دامنه را تأیید کنید. در فایل خصوصی محیط همان نصب، `SITE_URL=https://chapgiti.ir` و پس از تصمیم عمومی‌سازی، `INDEXING_ENABLED=true` تنظیم شود. فرایند باید در پنجرهٔ مجاز استقرار، محیط جدید را بخواند. سپس صفحهٔ اصلی، مقالهٔ منتشرشده، robots و sitemap را مرور کنید. در توسعه indexing خاموش است. پیش‌نویس، حساب، مدیر، محاسبه‌گر نیازمند ورود، تیکت و فایل خصوصی در sitemap جای ندارند.

1. در Search Console یک Domain Property برای `chapgiti.ir` بسازید. رکورد TXT اعلام‌شده را در DNS دامنه ثبت و Verify کنید. [تأیید مالکیت دامنه](https://support.google.com/webmasters/answer/9008080)
2. در بخش Sitemaps نشانی `https://chapgiti.ir/sitemap.xml` را ارسال و وضعیت دریافت و پردازش را بررسی کنید. [راهنمای Sitemap](https://support.google.com/webmasters/answer/7451001)
3. در URL Inspection صفحهٔ اصلی و یکی از مقاله‌ها را آزمایش کنید و canonical انتخابی و امکان خزیدن را بررسی کنید. در Pages علت حذف یا خطای صفحات عمومی را پیگیری کنید. زمان و رتبهٔ نمایش را گوگل تعیین می‌کند. [بازرسی URL](https://support.google.com/webmasters/answer/9012289)
